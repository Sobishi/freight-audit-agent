# R1: rule IDs and audit run logs

## What changed

The calculations and duplicate matching keys have not changed. This release
adds traceability to existing results. Charge-type-aware matching is R2.

## Rule catalogue

The catalogue is in `audit_engine/rules.py`. Each rule has an ID, version,
description and implementation status. Planned rules cannot be recorded as
executed. Increment a rule's version when its decision logic changes.

Implemented rules:

* REP-01: repeated AWB, requiring review, not proof of duplicate billing.
* DUP-01: positive repeated charge matching AWB, carrier and amount. Still a
  potential duplicate, not a confirmed claim. Charge type is not yet a key.
* CR-01: negative repeated-AWB line classified as credit or reversal. It is
  not yet matched to an original charge or deducted from exposure.
* ADJ-01: zero-value repeated-AWB adjustment.
* DATA-02: missing carrier or service information.
* BASE-01: missing base freight amount.
* RATE-01: carrier/service rate not found.
* RATE-02: billed freight above carrier/service rate, outside tolerance.
* UNDER-01: billed freight below carrier/service rate, outside tolerance.

Planned: DATA-01, POD-01, WT-01, WT-02, SUR-01, TAX-01.

A matched rate has no finding ID. Overlapping missing-information flags retain
both IDs. Finding IDs identify results; the run's completed-rule list identifies
checks that ran, including checks that found no exceptions.

## Run log

Every audit started through `main.py` after argument parsing creates one JSON
record in `logs/`. Change the folder with `--log-dir`. Direct function calls do
not create logs automatically.

The record contains:

* Unique run ID, UTC start/end timestamps, duration and status.
* Input basenames and SHA-256 hashes, including rate cards and carrier config.
* Code hashes and installed runtime library versions.
* Selected carrier, sheet, header, fallback option and effective tolerance.
* Rule IDs/versions started and completed.
* Aggregate invoice-line, finding, rate-status and held-line counts.
* Output report hash, when a report is produced.
* Failure type and stage, without copying the exception message.

The log does not contain invoice rows, AWBs, customer records or financial
amounts. Financial totals remain in the audit report; the log avoids combining
currencies or duplicating financial data. File names and settings can themselves
be sensitive, so keep logs private.

If an input changes during processing, the run fails its integrity check. Do
not use any outputs from that run. A failed run is not a successful audit. A
process killed before completion may leave a `running` record; investigate it.

These are local operational logs, not immutable or tamper-proof records.
Restricted storage, retention policy and central logging belong to later
production deployment. The hash identifies bytes; it does not store the file
or prevent the same invoice from being processed again.

CLI syntax errors and `--help` happen before the audit starts and are not logged.
A log write failure is surfaced rather than silently ignored.

## Report additions

* Audit Findings: Rule ID, Rule Version, Rule Description and source Invoice
  Line ID when available.
* Rate Validation: Rule IDs, Rule Versions, Rule Descriptions and Rate Basis.
* Audit Summary: Audit Run ID for reports generated by the CLI.
* Exposure Reconciliation: Rate Exposure Status and Payment Treatment, so
  unknown exposure remains visibly unknown rather than just a numeric zero.

## Apply this patch

Save `phase_r1_rules_and_run_log.patch` in the project root. Run each command
separately. Start with a clean working tree, except for the downloaded patch.

```bash
git status
git apply --check phase_r1_rules_and_run_log.patch
git apply phase_r1_rules_and_run_log.patch
python -m pytest tests/ -q
```

Expected: 230 passed with the demo workbook, or 228 passed and 2 skipped without
it. No new dependency is required. These counts assume no other tests were added.

Before staging, ignore logs and patch files. This bundle does not include your
existing `.gitignore`, so the patch does not overwrite it.

```bash
echo "logs/" >> .gitignore
echo "*.patch" >> .gitignore
rm phase_r1_rules_and_run_log.patch
git add audit_engine/audit.py audit_engine/rate_validation.py audit_engine/rules.py audit_engine/run_log.py main.py reporting/excel_report.py tests/test_rule_traceability.py tests/test_run_log.py docs/rule_ids_and_run_logs.md .gitignore
git status
git commit -m "Complete R1: rule IDs and audit run logging"
git push origin main
```

Do not commit generated logs, reports or bundle files. The patch itself changes
9 files. Your `.gitignore` is a separate tenth change if modified above.

## Try a logged run

```bash
python main.py tests/fixtures/carriers/swiftline_invoice.csv --carrier swiftline
```

This runs duplicate checks only because no rate card was supplied. The terminal
prints the log path. To also validate rates, add `--rates` with your agreed-rate
file. Existing rate checks still use carrier and service, not zone or weight.
